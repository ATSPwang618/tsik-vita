# 排错

排查前保留存档，记录当前 VPK／清单 hash、语言、剧情位置、操作步骤与实机截图。源码构建成功不能替代设备复现。

## 启动错误

| 提示 | 处理 |
| --- | --- |
| `MISSING FILE OR FOLDER` | 检查 `ux0:data/TSUKIHIME-RE/assets/` 及目录套层 |
| `WRONG FILE SIZE` | 先确认使用大文件修复 VPK；再对照清单核对具体文件长度 |
| `WRONG ASSET VERSION` | 校对 VPK、清单和升级范围，勿混用 R3／R4 或魔夜素材 |
| `FILE READ FAILED` | 检查文件可读性、传输和存储介质；保留具体文件名 |
| `ENGINE PROFILE ERROR` | 重新生成匹配的内嵌 profile 并构建 |

不要删除检查或手改清单使错误消失；先查实际原因。

## 超过 2 GiB 的主归档

历史故障时实机 `w_allpac.mrg` 为 2,475,186,176 字节，与本地和 profile 一致；设备清单与上一性能包的 eboot 身份也已只读核对。这次 `WRONG FILE SIZE` 的原因是旧接口的 32 位文件长度／seek 截断。

Vita newlib `off_t` 为有符号 32 位，当前长度被表示成 -1,819,781,120，再转成 Rust metadata 的 u64 后是 18,446,744,071,889,770,496。newlib `_lseek_r` 还调用 `sceIoLseek32`，只绕过启动比较仍会影响后半段资源。

现由 `knife-core/src/file_io_native.rs` 直接拥有 SDK SceUID，调用 `sceIoOpen/Read/Lseek/Close`。`sceIoLseek` 使用 64 位 `SceOff`，查询大小后恢复原位置；负返回值和超出 i64 的偏移保持错误。启动检查和所有 MRG 入口共用这一层，保留精确大小、CRC、短读与 extent 检查。

**CPU 和可执行文件仍为 ARMv7 32 位，只有文件位置数值使用 64 位。** 相关[设备身份记录](evidence/large-file-diagnosis.json)与[ARM 反汇编](evidence/native-seek-arm.txt)已保留。额外 FTP 范围读取被断开，未计为设备 CRC 校验通过；也未声称已完整 hash 设备归档。

上述是历史大文件故障。当前稳定版主归档为 819,984,384 字节，大小检查继续精确匹配；从旧高清包升级时必须更新[配套 7 文件](assets.md#升级范围)。

## 字体、音乐与 CG

音乐列表、时间／音量缺字的旧问题来自仅含两个补充字形的字体被当作主字体，现使用主字体优先。若仍为空，核对当前 VPK、双语言字体包、素材版本和鉴赏解锁状态。

早期 CG 不显示是 KIMG／KATL 加载路径不匹配；后续缩略图模糊来自整页过度缩小，R4 改为分页及对应 ID。更新范围见[素材说明](assets.md#升级范围)，不能只替 VPK 就期待旧缩略图文件变清晰。

## 标题／菜单按钮不可见但仍能操作

R4 清晰度重建保留了宽图和长图，旧 `defer_source` 却仍限制宽 ≤960、高 ≤1080。例如标题背景 `title_bg0` 为 1335×633，菜单的 `flow_thumb_all_zc` 为 1040×832。登记这一个成员失败会使 `ui_textures` 整组返回错误，包含按钮的已登记部分也被丢弃；输入逻辑与声音仍运行。

已针对全部 24 个图集／438 成员检查并修正 GXT 轴限制，同时保留 960×1080 物理像素预算。旧代码会拒绝 15 个成员，影响日中 CONF/DISP/MENU/TITLE 八个图集和 EFFECT 一个图集。236 张实际 GXT 能解析解码，标题／菜单共 60 个状态区域具有可见 alpha。轴限制修复在引擎且继续保留；当前稳定版另外变更剧情素材，升级须遵循[配套范围](assets.md#升级范围)，UI 归档本身未降采样。

若新版仍有个别界面缺图，在 VitaDeck 保存含版本标识、`UI atlas ready` 或 `ui textures ...` 的日志，并记录语言、页面及切换步骤；离线检查不能替代所有 UI 的实机验收。

## 剧情暂停：CDRAM 物理页不足

用户提供的 `2026-11-02-015319.jpg` 与日志对应 scene=1、pc=5309。失败资源为 `AOK_A_21_00_N01_03_03`，不是尺寸超界或文件损坏：`effects texture CDRAM allocation: 0x80024309` 在 VitaSDK 中为 `SCE_KERNEL_ERROR_NO_FREE_PHYSICAL_PAGE_CDRAM`。它的物理尺寸为 1020×1016，RGBA 为 4,145,280 字节，加行距为 4,161,536 字节，新物理页要 4 MiB。附近采样报告空闲 15 MiB，不能据此保证一次物理分配成功，也不能仅凭此日志证明具体碎片分布。

旧准入只查看可用字节，真正上传失败后不会再进入缓存回收。现在准入先取得实际存储，压力时回收闲置、可重新加载的纹理；一帧需要的全部纹理保持 pin，回收次数受候选数量限制。不可恢复的 SDK 错误仍中止，不会把损坏素材假装加载成功。`parts #3` 的 GXT 错走普通 PNG/JPEG 路径也已一并修正。

本版进一步按用户要求在电脑端提前缩小全包剧情图片：失败图片物理尺寸改为 360×359，RGBA 新页从 4 MiB 降至 512 KiB；其余剧情图也受到同一最坏展开上限约束。换图／调色开始前释放可选离屏与最近文字缓存，已记录资源仍由 GPU 完成 fence 保护。必需画布与演出语义保留，详见[性能](performance.md#内存上限)。

更新当前 VPK 和[7 个素材文件](assets.md#升级范围)，保留存档／配置，完全退出后重启。新引擎与旧高清包不能混用。整包离线扫描和 80 张旧新 RGBA 的压力夹具通过；是否跨过该实机剧情及长时间运行仍未验证。原始错误与历史身份见[诊断](evidence/cdram-diagnosis.json)，当前身份见[验证](evidence/current-validation.json)。

## CG 两侧浅灰边

森林原图 1404×844 并非 16:9，完整适配后约 898.3×540，在灰底查看器中左右各留约 30.9 像素。旧摇杆没有死区，中心漂移可将图片移向一侧，形成约 62 像素单侧灰条。代码已加入 ±16 死区；截图本身不能证明当时摇杆数值。

SELECT 可切换为保持比例的铺满显示，会裁掉少量上下内容。不要拉伸图片来消除正常比例留边，也不要把所有立绘都强制重采样成整屏大小。

## 资源失败与设备日志

游戏提示素材损坏或无法继续时，保留 `ux0:data/TSUKIHIME-RE/resource-error.json`（如生成），记录具体语言／章节和触发步骤。当前正式包默认启用 VitaDeck/CatLog 控制台，失败文件记录也保留。模块加载工具中的单条警告不应脱离真实错误画面直接当作故障根因。

没有实时输出时检查 VitaDeck 的日志接收是否打开及 CatLog 是否沿用魔夜的正常配置；FTP 连通不能证明日志通道连通。确认启动的是 `KNIF00541`、当前日志 build tag 为 `tsukihime540-offline-shaders-20261106`。用户提供的上一版 `tsukihime540-ui-log-20261102` 实机日志已包含运行警告与性能窗口，证明那一版的日志链路有实际输出；新包身份需再次核对。性能记录缺失还应检查根目录／assets 中的 `perf-enable.txt` 是否显式关闭，详见[实时日志说明](performance.md#vitadeck-实时日志)。

当前月姬离线 shader 包不读取或写入旧 shader cache。启动日志应出现 `mode=offline`；新增专用变体的准入与 A/B 排查见[离线 shader](shaders.md)。
